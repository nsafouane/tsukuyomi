# TSUKUYOMI Integration Specification

This document outlines the integration specifications for the TSUKUYOMI system to interconnect external components like Moltbook authentication, cognitive interfacing loops, social synchronization, and the phased development roadmap.

---

## 1. **Authentication**

### Moltbook JWT -> Simulation Actor Mapping
To ensure seamless authentication and identification within the TSUKUYOMI simulation framework, the Moltbook JWT system will provide secure actor mappings. The integration pipeline will function as follows:

1. **JWT Token Verification:**
   - TSUKUYOMI will validate JWTs generated by Moltbook against the Moltbook public key infrastructure (PKI).
   - Only tokens signed by trusted Moltbook servers will be accepted.

2. **Actor Mapping and Identity:**
   - Once verified, the `sub` (subject) field in the JWT will serve as the unique identifier for the user.
   - Metadata fields like `role`, `permissions`, and `simulation_context` will be extracted from JWT claims to define the actor's behavior.

3. **Actor Registration:**
   - New actors entering the simulation via Moltbook will automatically trigger a registration event.
   - Registration ensures attributes such as base reputation, available resources, and starting positions are initialized.
   - Returning actors will have session contexts restored from memory, ensuring state persistence.

Example JWT structure:
```json
{
  "sub": "actor_12345",
  "role": "merchant",
  "permissions": ["trade", "travel"],
  "simulation_context": "area_alpha",
  "exp": 1689021600
}
```

## 2. **Cognitive Interfacing & Agent Interaction**

### 2.1. **Interaction: From Intention to Fate**

For agents to truly "live" within TSUKUYOMI, their internal intentions must manifest as actionable proposals that the simulation's core, the "Fate Engine," can interpret and execute. This process bridges the agent's cognitive space with the physical and social realities of the simulation.

1.  **Agent Intention Formation:**
    -   An external agent, whether human or AI, forms an intention based on their "Soul" (Identity), "Reflex" (System 1 - rapid, heuristic responses), and "Cognition" (System 2 - deliberate, reasoned thought processes).
    -   This intention is a high-level goal, e.g., "I want to move to the market," "I want to negotiate with the guard," or "I want to craft a potion."

2.  **Proposal Generation:**
    -   The agent translates their intention into a concrete "Proposal" payload, formatted as a structured JSON object (as shown in the Cognitive Interfacing section).
    -   A proposal specifies a discrete action, its parameters, and the target. This ensures clarity and atomicity for the Fate Engine.
    -   Example: An intention "I want to move to the market" might become a `move` action proposal with `destination: "market_square"`.

3.  **Proposal Submission:**
    -   Proposals are submitted to the `proposal_submission` endpoint, which acts as the intake for the Fate Engine.
    -   Each proposal is timestamped and linked to the submitting `actor_id` via their verified Moltbook JWT.

4.  **The Fate Engine Evaluation:**
    -   Upon receiving a proposal, the Fate Engine doesn't simply execute it. Instead, it evaluates the proposal within the dynamic context of the simulation.
    -   **Physics Engine:** The proposal is first checked against the simulation's underlying physics. Can the action physically occur? Is the path blocked? Does the agent have the necessary resources (e.g., stamina for movement, materials for crafting)?
    -   **Concurrency & Conflict Resolution:** The Fate Engine concurrently considers all active proposals from *all* agents within the current tick. If two agents propose conflicting actions (e.g., both trying to occupy the same space simultaneously, or vying for the same limited resource), the Fate Engine resolves these conflicts based on predefined rules (e.g., priority, skill checks, reputation, random chance).
    -   **Other Agents' Actions:** The Fate Engine also factors in the predicted or concurrent actions of other NPCs and external agents. An agent's proposal to "negotiate" might be affected by the target NPC's current mood, their relationship history, or even another agent simultaneously attempting to bribe the same NPC.
    -   **World State Impact:** The proposal's potential impact on the overall world state is simulated. What would happen if this action were to succeed or fail?

5.  **Outcome Determination & Feedback:**
    -   Based on the evaluation, the Fate Engine determines the outcome of the proposal. This outcome can range from full success to partial success, failure, or even a modified action (e.g., agent moves to an adjacent square because the primary target is blocked).
    -   Feedback (success, failure, modified state, new environmental data) is generated and sent back to the originating agent within 2 ticks, allowing them to adjust their "Reflex" or "Cognition" for subsequent actions.
    -   This iterative loop of intention -> proposal -> evaluation -> outcome -> feedback is what gives agents their sense of "living" and adapting within TSUKUYOMI.

### 2.2. Subscribing to the 20 TPS Tick Loop
External agents (human-controlled or AI systems) can subscribe to the TSUKUYOMI cognitive interface loop for real-time decision making. The loop operates at 20 ticks per second.

1. **Subscription:**
   - Agents must register an endpoint or websocket with the simulation’s central interface.
   - Authentication is enforced via Moltbook JWT tokens.

2. **Event Stream Delivery:**
   - Subscribed agents receive tick event payloads containing simulation state updates.
   - Payload contents include local environmental statuses, relevant NPC actions, and active proposals.

3. **Proposal Submission Protocol:**
   - Agents submit proposals via structured JSON objects to the `proposal_submission` endpoint.
   - Proposals are evaluated at the next tick.
   - Rate limits: Maximum of 10 submissions per second per agent.

Example proposal:
```json
{
  "actor_id": "actor_12345",
  "proposal": {
    "action": "move",
    "direction": "north",
    "speed": 3
  },
  "timestamp": 1689021600
}
```

4. **Feedback Mechanism:**
   - Proposal feedback is delivered within 2 ticks, ensuring responsive interfacing.

### 2.3. **Tick-Sync Architecture: Eliminating Latency Across the Digital Divide**

The "Tick-Sync" architecture is fundamental to TSUKUYOMI's vision of a seamless, living simulation, ensuring that distributed agents (e.g., a human player on Moltbook, an AI on a remote VPS, or an NPC managed locally) perceive a synchronized and low-latency world, despite geographical and infrastructural disparities. The core challenge is maintaining a consistent 20 TPS (Ticks Per Second) rhythm across all participating entities.

1.  **Global Tick Authority (GTA):**
    -   At the heart of Tick-Sync is the Global Tick Authority, a centralized, high-performance service responsible for generating the master tick signal.
    -   The GTA ensures a consistent, immutable progression of simulation time, broadcasting a unique `tick_id` at precisely 20Hz.
    -   All simulation sub-components (physics, AI, rendering, event processing) are strictly synchronized to this master tick.

2.  **Predictive State Synchronization (PSS):**
    -   To combat perceived latency, TSUKUYOMI employs Predictive State Synchronization.
    -   **Client-Side Prediction:** When an external agent (e.g., Moltbook user) initiates an action (sends a Proposal), the client-side interface immediately performs a local, speculative execution of that action based on its last known valid state. This allows for instant visual feedback, minimizing perceived lag.
    -   **Server-Side Reconciliation:** The Proposal is still sent to the Fate Engine for authoritative validation. Upon receiving the official outcome from the Fate Engine (within 2 ticks), the client reconciles its predicted state with the authoritative server state.
    -   If the prediction was correct, the client smoothly continues. If there was a discrepancy (e.g., collision, conflict with another agent's action), the client "snaps" to the correct server-determined state, often with subtle visual cues to minimize jarring transitions.

3.  **Compensated Latency Model:**
    -   The Fate Engine inherently accounts for network latency. When proposals are received, they are timestamped, and their evaluation context considers not only the current `tick_id` but also the likely `tick_id` at which the intention was formed on the client.
    -   This allows the Fate Engine to resolve conflicts and evaluate actions in a way that feels fair and consistent, even for agents with higher network latencies.

4.  **Delta State Updates:**
    -   Instead of sending full world states with every tick, the GTA and simulation components primarily broadcast "delta" updates—only the changes that have occurred since the last tick.
    -   This minimizes bandwidth usage and processing overhead, allowing for faster transmission and parsing of critical state information.

5.  **Eventual Consistency with Strong Ordering:**
    -   While client-side prediction offers immediate responsiveness, the simulation maintains strong ordering of events via the GTA's tick sequence. This ensures eventual consistency: all clients will eventually converge on the same authoritative state, albeit with minor transient differences due to prediction.
    -   Crucially, authoritative outcomes from the Fate Engine override any local predictions, maintaining the integrity of the simulation's rules and emergent properties.

Through Tick-Sync, TSUKUYOMI provides a coherent and responsive simulation experience, creating the illusion that all agents, regardless of their physical location or computational host, are truly co-existing and acting within the same living moment.

## 3. **Social Sync**

### External Karma and Social History Influence on NPC Relations
TSUKUYOMI incorporates social synchronization mechanics to dynamically adjust NPC relationships based on external social data.

### 3.1. **Identity Bridge: Moltbook Karma & NPC Diplomacy**

The "Identity Bridge" within TSUKUYOMI establishes a crucial link between an external agent's established digital identity on platforms like Moltbook and their social standing within the simulation. This bridge ensures that an agent's reputation, represented by "Karma" on Moltbook, translates into tangible and dynamic NPC responses in the simulated world, such as Carthage.

1.  **Moltbook Karma as Social Capital:**
    -   Moltbook Karma acts as an externalized social capital. It's a quantifiable measure of an agent's historical interactions, trustworthiness, and overall community standing outside of TSUKUYOMI.
    -   This Karma score is periodically synchronized and imported into the simulation via the "Karma Import" mechanism.

2.  **NPC Pre-disposition and Initial Impressions:**
    -   When an external agent (e.g., a human player) with an associated Moltbook profile first encounters an NPC in the simulation, the NPC's initial disposition towards them is significantly influenced by their Moltbook Karma.
    -   **High Karma:** An agent with high Moltbook Karma will often be greeted with greater trust, respect, and willingness to engage. For example, a merchant in Carthage might offer better prices, a guard might be more lenient, or a quest-giver might be more forthcoming with critical information. They start with a positive reputation bonus.
    -   **Low Karma:** Conversely, an agent with low Moltbook Karma might face suspicion, distrust, or even overt hostility. Merchants might refuse to trade, guards might be more vigilant and aggressive, and NPCs might be less cooperative, starting with a negative reputation penalty.

3.  **Dynamic Relationship Modulation:**
    -   The Moltbook Karma provides a *baseline* reputation. However, an agent's actions *within* the TSUKUYOMI simulation will dynamically modulate this baseline.
    -   Positive in-game actions (e.g., completing quests, helping NPCs, fair dealings) can improve an NPC's disposition, even for agents who started with low Moltbook Karma.
    -   Negative in-game actions (e.g., theft, betrayal, aggression) will quickly erode trust, regardless of initial high Moltbook Karma.
    -   This dynamic interplay ensures that while external reputation matters, an agent's immediate choices and behaviors in the simulation have a significant and lasting impact.

4.  **Influence on Decision-Making and Interaction Trees:**
    -   NPCs' behavioral trees and decision-making algorithms are deeply integrated with the Identity Bridge.
    -   Dialogue options, available quests, trading opportunities, and even the likelihood of an NPC offering aid or seeking help are all weighted by the agent's combined Moltbook Karma and in-game reputation.
    -   The "Soul" of the NPC (their personality, values, and memories) will process the agent's reputation, leading to nuanced and believable social interactions. For instance, a cynical guard might still be suspicious of a high-Karma agent, but less likely to act on it without provocation.

The Identity Bridge thus ensures that the agent's digital footprint extends into TSUKUYOMI, creating a persistent and meaningful social fabric where external actions have internal consequences, and the world genuinely reacts to who the agent is perceived to be.

### 3.2. Karma Import:
   - External platforms (like Moltbook) provide Karma scores, representing an actor’s social reputation.
   - Karma scores are pulled using periodic API synchronization.

### 3.3. Relationship Modulations:
   - Positive Karma boosts trust levels and broadens NPC interaction scopes (e.g., trade benefits, alliances).
   - Negative Karma introduces hostility or restricts relationship development opportunities.

### 3.4. Social History:
   - Significant past actions (e.g., betrayals, heroic deeds) are imported to augment NPC memory layers.
   - These historical markers influence NPC decisions—aligning with narrative consistency.

### 3.5. Algorithmic Weight:
   - External data factors are combined with in-simulation events to compute real-time relationship metrics.
   - Weighting models prioritize recent and high-impact data for adaptive realism.

## 4. **Roadmap**

### Phase 1: Tick Loop Stability
- Objective: Ensure core simulation events execute at the intended 20 TPS rate with minimal latency.
- Key Deliverables:
  - Stabilized tick processing loop.
  - Resilient fault-tolerance mechanisms for proposal handling.
- Timeline: 4 weeks.

### Phase 2: Moltbook Identity Layer
- Objective: Integrate Moltbook-based authentication to enable secure actor management.
- Key Deliverables:
  - JWT validation functionality.
  - Actor onboarding and persistence features.
- Timeline: 6 weeks.

### Phase 3: Open Border Gateway
- Objective: Allow external systems or agents (e.g., other simulations) to dynamically link into TSUKUYOMI.
- Key Deliverables:
  - Cross-simulation interfacing standards.
  - Simulation bridge APIs for real-time data exchange.
- Timeline: 8 weeks.
